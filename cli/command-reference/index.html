Registry Generation​

Generate a starter registry from local Git checkouts:

x4 registry init \
  --repo ~/dev/repos/app \
  --repo ~/dev/repos/api \
  --repo-set current-work \
  --output ~/dev/x4/current-work.registry.yaml \
  --install skip

The generated file is a reviewable starting point. It infers repo ids, remotes, default branches, package-manager setup commands, basic test commands, env allowlists, an env bundle placeholder, and a metadata-only sandbox profile.

Safety Defaults​

  • Mutating GitHub and remote-control commands usually default to dry-run or planning mode.
  • Preview comments refuse local-only URLs.
  • Cleanup dry-run is recommended before force cleanup.
  • Env commands validate key names without printing secret values.
  • x4 sandbox clear requires --all and either --dry-run or --force; it only targets X4-labeled sandbox resources.
  • x4 sandbox status reconciles saved service-sandbox state against X4-labeled Docker containers before showing preview links as live.
  • x4 sandbox run "<goal>" is the preferred interactive sandbox path: it writes a harness goal under .x4/ai/runs/, asks the selected AI engine to propose a sandbox profile for the current workspace goal, validates the profile, and only then runs deterministic sandbox startup. If startup fails, it retries with AI repair feedback up to --ai-attempts times, defaulting to 3.
  • x4 sandbox up --ai is the lower-level experimental shortcut when a script already knows the exact profile to prepare before startup.
  • Use AI only where discovery is the hard part, such as inferring sandbox service commands, ports, routes, and health paths. Keep workspace creation, registry validation, env filtering, cleanup, and PR operations deterministic.
